# Feature Acceptance — original user goal, not Task technical completion

Use only when Arca evaluates delivered feature-level behavior against its effective approved goal/brief/Feature Contract revision. KAGARI's Task PASS, merged PR, release artifact, deployed operation and research hypothesis validity are **different** evidence claims.

Read the original user goal, selected Issue ACs/non-goals, actual KAGARI Task Evidence and directly observed user workflows. For each minimum behavior name its environment and classify:
- **goal-satisfied:** demonstrated actual user-visible behavior covers the approved minimum.
- **in-spec-defect:** implementation violates the approved Issue; return reproduction and evidence to the existing KAGARI Task's technical correction loop.
- **specification-goal-mismatch:** the approved Issue itself fails the original intended outcome; ask Human about the affected requirement rather than instructing KAGARI to redesign the product.
- **unknown:** operation/evidence missing or stale; state the smallest observation necessary and do not declare success.

Optional enhancement or production-only assurance not required by the accepted minimum does not block this acceptance. Conversely an unmet original must-have cannot be relabeled optional solely because technical tests passed.

Report what users can actually do, where it works, unverified limits and the next owner. Reuse the existing human agreement; **no new ceremonial acceptance gate** is created when the decision is already settled. New Issue/phase, substantive risk, Merge, publication and installed Plugin updates remain separately Human-authorized.
